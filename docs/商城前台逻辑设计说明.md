## 1. 现状盘点（front/ 14 页）

| 事实 | 说明 |
|---|---|
| 纯静态演示 | 商品/金额/订单/地址全部写死，无任何真实接口调用 |
| 唯一本地存储 | 购物车 localStorage `shop_cart_guest`（js/main.js `ShopCart` 管理） |
| 金额不一致 | checkout/address/address-add/address-edit 各页写死 ¥7636 / ¥7237 / ¥6499 三套，与购物车不联动 |
| 页面命名误导 | address.html 实为"有地址确认订单"；checkout.html 为"无地址确认订单"；address-add/edit 为地址弹窗复刻页，标题都叫"确认订单" |
| 后端缺口 | 后端只实现了 B 端（RBAC 管理端 auth/permission/goods），面向会员的 C 端接口一个都没有；数据库已建 orders/members/coupons 等表，但**缺购物车表与收货地址表** |

结论：front 要做真实可用，必须"后端补 C 端接口 + 两张新表 + 前端逐页重写逻辑"三件事一起做，单改前端只会得到又一个假壳。

## 2. 设计原则

1. **C 端独立前缀 `/api/v1/shop/*`**：与 B 端 `/api/v1/*`（带权限码）物理隔离，避免游客/会员误触管理接口，也避免权限码体系污染会员端。
2. **与后台同库同口径**：商品、订单、会员、优惠券全部读写后台已建的同一批表；订单状态机、库存原子扣减、营销叠加规则直接复用后台 spec，C 端不另立一套，否则两边数据对不上。
3. **钱只在服务端算**：购物车/结算页展示的金额只是"预览"，应付金额一律由 `POST /shop/orders/preview` 服务端返回，提交订单时服务端重新计价，前端禁止自算应付。
4. **登录态分层**：游客可看（首页/搜索/详情/购物车本地），要花钱/要管资产（结算/地址/订单/支付/售后/优惠券/积分）必须登录；未登录访问需登录页时跳 `login.html?redirect=<原页>`，登录成功回跳。
5. **游客购物车可无损升会员**：游客把商品放 localStorage（新键 `shop_cart_guest`），**登录成功即统一触发** `POST /shop/cart/merge`（items 含 selected，见 spec §5.4/§8.13）并入服务端 `member_cart`，合并成功清本地后再执行 redirect 回跳，此后以服务端为准。
6. **支付演示可替换**：`POST /shop/pay/{id}` 演示直接置已支付；将来接微信/支付宝只改这一处为"下单网关 + 回调"，页面轮询接口不变。

## 3. 关键设计决策记录（评审重点）

| 决策 | 理由 | 备选（未选） |
|---|---|---|
| C 端前缀 /api/v1/shop | 命名空间隔离、路由清晰 | 复用 B 端模块加游客放行（会破坏权限语义） |
| 购物车分"游客 local + 会员服务端"两态 | 无账号也能加购、体验顺；下单前必须登录 | 一律要求登录才能加购（流失率高）；一律服务端（游客无会话） |
| 新增 member_cart / member_address 两表 | 后端现有表无此二实体，购物车/地址无法持久化 | 地址塞 order receiver 冗余（无法管理多地址）；购物车继续纯本地（跨设备丢） |
| checkout.html 与 address.html 归并成"单页结算确认 + 地址管理" | 现状两页同一职责、金额三处写死，是历史债 | 保留现状逐页打补丁（继续不一致） |
| 支付状态用轮询而非跳转硬等 | 模拟收银台需要确定终态 | 按钮 alert 假成功（现状，不可用于真下单） |
| 会员 token 与 admin token 分离（载荷 typ 区分） | 防止会员 token 调 B 端接口越权 | 共用一套 token（安全风险） |
| 结算/地址/订单/支付等一律需登录 | 主流电商做法；订单与地址是账户资产，匿名下单售后无主 | 游客填地址也能下单、付款前才登录（订单归属与退款无解） |
| 省市区走后端区域接口（region 表 + 级联下钻）而非前端静态字典 | 后期补全国全量区划只需扩 seed 数据，接口与前端零改动；避免静态字典每次扩充都改前端且脱离 seed 治理 | 前端静态字典（仅 demo 三组可用，扩充成本高） |
| 售后边界按 spec §10 规则 8 表格执行 | 与订单状态机逐态对应、防漏风防重复，前端按钮由 actions 驱动 | 无边界随意发起（状态混乱、退款失控） |
| 会员评价排期 S5（紧随 S4 订单全链路） | 评价合法性须"已完成订单本人"校验，依赖 S4 买→付→发→收真实数据；早做只能造假单，自验收无据 | V1 不做评价（功能缺口）；S0 早期做（无真实订单可评） |
| 下单幂等走 previewToken（preview 返回一次性 token、下单必带） | 防重复提交与参数篡改；服务端重计价兜底；spec 自洽（原文档"或同参"无生产者） | "同参重算+提交锁"（丢 preview 语义、防重弱） |
| 优惠券/积分/售后做独立页（after-sale/coupons/points，S6 新增，入口集中 orders 快捷条） | 页面职责单一、验收有载体、与 §5.9/5.10 接口一一对应 | 全部内嵌 orders（页过载）；只有接口无页面消费（评审高项 B3） |
| 登录成功即合并游客车，合并成功才执行 redirect 回跳 | 游客加购→登录→结算链路不断，合并时机唯一化不丢车 | 进结算页时才合并（redirect 回跳后车仍空，链路断裂） |
| 支付链路：payment 发起 → wechat-pay 模拟扫码轮询 → "我已完成支付"才 POST pay 置成功 → orders | 保留收银台页职责、与"轮询+人工确认"演示一致，消除直付成功后还进收银台矛盾 | pay 直成功跳过收银台（wechat-pay 变死页） |

> **决策记录（2026-09-03）**：① 设立"商城前台"为独立里程碑，按 spec §13 S0 开工；② 结算需登录（主流电商做法）；③ 省市区：先做区域接口 + 少量演示数据，接口契约 全国区划固定，后期仅扩数据；④ 评价要做，排 S5（见上表）；⑤ 售后边界按上表。已全部回写 `specs/商城前台V1.2.spec.md`（文件名随版本由 V1 演进为现用 V1.2，变更详见 spec §15）。
> **region 上线保留确认（2026-09-03）**：region 入 seed base 属长期保留字典——仅人工执行 `seed.runner base` 时  `code` 幂等 upsert（增补/更新），**不删不重置、不随部署/升级自动清理**；`clean-base/clean-demo` 仅为演示环境重建手段，不用于线上库。
> **定稿决策（2026-09-03）**：后台 V2 在该次评审时视为已完善、不再改动（注：后续 CHANGELOG 中记录的后台安全性修复不在此列）；评审仅落地前端完善项——spec 升 v1.2（下单幂等 previewToken、登录成功即合并游客车、券/积分/售后独立页 14→17、支付两段定稿、"无忘记密码走后台重置"+send-code 收敛 register、merge 带 selected、region 区划 code 不落库、引用统一为 §10 规则 N），详见 spec §15 变更记录与本决策表新增行。评审验收修正（同日并入 spec v1.2，⑨~⑮）：§10 规则 5 允许发起售后改 2/3/4、售后"待收货"归 2 处理中业务子阶段、§4.1 补 C 端实现基准注（全部 §5 契约由新增 shop 路由实现，命名不继承 B 端出入）、coupons/available 登录态对齐、错误码 3001~3005 逐码、规则 8 补售后结束订单回落句。

## 4. 页面职责与链路（17 页：14 既有 + S6 新增 after-sale/coupons/points 3 页，见 spec §3/§8.15~8.17）

```
[游客]                          [会员]
index ──搜索──▶ search ──点商品──▶ detail
  │                                 │ 加购
  │                                ▼
  │                           add-to-cart ──去结算──▶ cart
login ◀──register                (游客改数量/勾选/删 存本地)
  │登录                            │ 去结算(未登录→login?redirect=checkout)
  ▼                               ▼
login 成功(redirect 回跳)    checkout(结算确认)
                               │ 选/增/改地址: address / address-add / address-edit
                               │ 选支付方式/优惠券/积分
                               ▼
                      POST /shop/orders(服务端计价+扣库存)
                               ▼
                          payment ──▶ wechat-pay(轮询)
                               ▼ 支付成功
                          orders(我的订单: 待付款/待发货/待收货/已完成/已取消/售后中)
                               │ 待付款: 付款/取消  待收货: 确认收货/看物流
                               │ 已完成: 再次购买   (售后入口: 申请→售后流程)
                               ▼
                   订单状态机(与后台一致 1→2→3→4; 5取消; 6售后中)
```

## 5. 需要后端新增的清单（backend 侧工作量）

1. **表（schema.py）**：`member_address`、`member_cart`、`region`（DDL 见 spec §6，region 演示子集入 seed base）；可选 `sms_codes`。
2. **配置**：`MEMBER_JWT_SECRET`、`ORDER_PAY_TIMEOUT_MINUTES`、`SMS_MOCK`（spec §11）。
3. **路由/service/schema 各一组**（  spec §5 分模块）：
   - shop_auth（注册/登录/me/改密码/资料/验证码）
   - shop_home（首页聚合/公告/广告）
   - shop_goods（列表/详情/评论/浏览埋点/分类/品牌）
   - shop_cart（增删改查/合并/清空）
   - shop_address（地址 CRUD/设默认）
   - shop_region（区域级联下钻列表，V1 演示数据、契约支持全量）
   - shop_order（preview/下单/列表/详情/取消/收货/物流/再次购买）
   - shop_pay（发起/状态轮询）
   - shop_after_sale（申请/详情/列表/退货运单/撤销）
   - shop_coupon（我的券/可领/领取）
   - shop_points（余额/流水）
4. **测试**：shop 接口 pytest（注册登录→加购→地址→preview→下单→支付→订单 tab→售后闭环）。
5. **seed**：demo 已含 10000000001~03 会员，无需新增；member_cart/member_address 为空即可（登录后自建）；region 演示子集入 base（广东/北京/上海三级，见 spec §6.3）。region 治理：仅入 base 禁 demo、启动不自动执行、幂等 upsert（code 主键，不删不重置）、全量随版本发布追加；区划若需后台即时维护再剥离 seed 改后台功能。
