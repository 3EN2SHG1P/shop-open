## 1. 项目定位

| 项 | 内容 |
|---|---|
| 产品 | 商城后台管理系统（运营管理端） |
| 服务对象 | 商城运营人员、管理员、超级管理员 |
| 定位 | 为商城前台（`front/`）提供全链路后台管理能力：商品、订单、用户、营销、内容、系统设置、RBAC 权限、操作日志 |
| 形态 | 前后端分离。本 spec 约束**后端（FastAPI + MySQL）**与**前后端接口契约**；前端页面仅作功能对照与联调参考 |
| 运行部署 | 后端接口服务与后台管理系统/管理端（`manager/`，含登录 `login.html`）统一由 FastAPI 监听 **8001 端口**（`http://127.0.0.1:8001`，根路径自动跳转 `/manager/login.html`，`/api/v1/*`、`/api/docs`、`/api/v1/health` 同址、同源）；商城前台 `front/` 独立静态托管于 **8000 端口**（站点根=`front/` 目录，根路径 `http://127.0.0.1:8000/` 即商城首页，无 /front/ 路径），跨域调用 8001 接口（`CORS_ORIGINS` 放行 `http://127.0.0.1:8000` 来源，见 §12 安全约束） |

**一句话目标**：实现一个可运行、可部署、带完整 RBAC 四层权限（菜单/按钮/接口/数据）的商城后台 API 服务，前端可依据本文档独立实现页面与按钮级鉴权。

## 2. 技术栈硬约束（不可偏离）

| 领域 | 约束 | 说明 |
|---|---|---|
| 语言 | Python 3.10+ | 使用类型注解 |
| Web 框架 | **FastAPI** | 禁止换用 Flask/Django |
| ASGI 服务器 | uvicorn | 开发模式 `--reload` |
| 依赖管理 | **uv** | `uv init` 初始化、`uv add` 新增依赖；`pyproject.toml` 声明 + `uv.lock` 锁定 |
| 数据库驱动 | **aiomysql（全异步）** | 全项目统一，**禁止 PyMySQL 同步驱动直接进异步路由**；若确需同步库，仅允许经 `run_in_threadpool` 隔离且需在 README 声明理由 |
| 数据库 | MySQL 5.7+ | 库名默认 `aaashop`；地址/端口/账号/口令必须全部可配置（见 §10），仓库不含真实口令 |
| 认证 | JWT（Bearer Token） | `Authorization: Bearer <token>` |
| 密码存储 | bcrypt / passlib 哈希 | 禁止明文、禁止 MD5/SHA1 直接存密码 |
| 权限模型 | RBAC 四层 | 菜单 / 按钮 / 接口 / 数据 四级权限 |
| 路由组织 | FastAPI `APIRouter` 模块化 | 见 §7 目录结构 |

**明确禁止**：
- ❌ 不引入重量级 ORM（如 SQLAlchemy）——本 spec 要求轻量 + aiomysql，SQL 手写或轻封装。
- ❌ 不引入 Django Admin 等现成后台。
- ❌ 不把业务逻辑写在路由函数体内（controller 只做参数校验与编排，业务放 service 层）。
- ❌ 不使用全局裸 SQL 拼接（必须参数化，防注入）。
- ❌ 不在异步路由中直接调用同步阻塞数据库驱动（见上表）。

## 4. 全局接口契约

### 4.1 统一返回格式
所有接口响应体固定为：

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

- HTTP 状态码：成功一律 `200`；认证失败 `401`；无权限 `403`；资源不存在 `404`；参数校验失败 `422`；服务器异常 `500`。**code 与 HTTP 状态码独立**：HTTP 200 时 code 也可能非 0（如"库存不足"业务失败）。
- 分页数据结构固定为：

```json
{
  "code": 0, "message": "success",
  "data": {
    "list": [...],
    "total": 100,
    "page": 1,
    "page_size": 20
  }
}
```

### 4.2 字段命名规范（强制）
- **请求体与响应统一 camelCase**（如 `orderNo`、`payAmount`、`createdAt`）；**query 参数统一 snake_case**（如 `page`、`page_size`、`sort_field`）。
- **数据库字段统一 snake_case**（如 `order_no`、`pay_amount`、`created_at`）。
- 后端在 service 层完成 snake_case ↔ camelCase 转换，前端不做任何适配。
- 列表接口通用参数统一命名：`page`、`page_size`、`keyword`、`sort_field`、`sort_order(asc/desc)`、各类筛选参数以资源语义命名（如 `status`、`start_time`、`end_time`）。

### 4.3 路由规范
- 统一前缀：`/api/v1/{module}/{resource}`。
- 资源用**复数名词**；操作用 HTTP 方法语义（GET 查询 / POST 创建 / PUT 全量更新 / DELETE 删除）。
- 动作型接口：`POST /api/v1/{resource}/{id}/action`（如 `POST /api/v1/orders/1001/ship`、`POST /api/v1/goods/batch/status`）。
- **导出接口统一走 `GET /api/v1/{module}/{resource}/export`**，返回 `application/vnd.ms-excel` 或 `text/csv` 文件流（`Content-Disposition` 附件），筛选参数同列表接口。

### 4.4 认证与鉴权
- 登录接口：`POST /api/v1/auth/login`，入参 `{ username, password }`，返回 `{ token, user }`。
- 除登录、健康检查外，**所有接口**都必须携带 JWT，通过 FastAPI 依赖注入统一校验：

```python
Depends(get_current_user)
Depends(require_permission("order:add"))
```

- 鉴权依赖执行顺序：**登录态 → 接口权限 → 数据权限**。

### 4.5 全局错误码字典

| 错误码段 | 含义 | 前端处理建议 |
|---|---|---|
| 0 | 成功 | - |
| 1000–1099 | 认证类（1001 token 过期/无效、1002 未登录、1003 登录失败次数超限） | 1001/1002 跳登录页；1003 提示锁定 |
| 2000–2099 | 参数类（2001 参数校验失败、2002 分页越界） | 高亮表单错误 |
| 3000–3099 | 业务类（3001 库存不足、3002 状态不允许此操作、3003 存在子节点/关联数据不可删除、3004 重复数据、3005 优惠不可叠加） | 按业务分支提示 |
| 4000–4099 | 权限类（4001 无接口权限、4002 无数据权限） | 提示无权限 |
| 5000–5099 | 系统类（5000 服务器内部错误） | 通用错误提示 |

## 7. 数据库设计（核心约束）

### 7.1 全局约定
- 表名小写下划线；主键统一 `id BIGINT UNSIGNED AUTO_INCREMENT`。
- 通用字段：`created_at`、`updated_at`（DATETIME，默认 CURRENT_TIMESTAMP / ON UPDATE）。
- **核心业务表统一增加 `created_by BIGINT UNSIGNED NOT NULL DEFAULT 0`**（数据权限 data_scope=1 的依据；0 表示系统/未知创建人）。实际落地范围为 16 张核心业务表（goods_category、brands、specifications、attributes、goods、orders、after_sales、points_logs、coupons、seckill、full_discount、group_buy、distributor、articles、notices、freight_templates）；明细/关联表（goods_sku、goods_images、goods_comments、order_items、order_logs、coupon_receive、members、member_address、member_cart 等）不强制该列，其可见范围随所属主表走。
- 金额字段统一 `DECIMAL(10,2)`；**禁止用 FLOAT/DOUBLE 存金额**。
- 状态字段统一 `TINYINT`，0 = 禁用/关闭，1 = 启用/正常，特殊状态用约定枚举并注释。
- 所有外键关系用逻辑外键（只存 id，不建物理 FK）。
- 时间字段统一 DATETIME；金额比较一律用 DECIMAL 运算。
- **业务时区统一 Asia/Shanghai（UTC+8，2026-09-05 增补）**：所有业务时间字段（`created_at` / `updated_at` / `last_login_time` / `locked_until` / 业务起止时间等）字面量基准为东八区。MySQL 数据库连接必须在连接建立时执行 `SET time_zone='+08:00'`（`core/database.py` 通过 `init_command` 注入并由 `_ensure_tz` 兜底），确保 `DEFAULT CURRENT_TIMESTAMP` 落库字面量为 CST；Python 端显式写入 DATETIME 时统一通过 `core/timezone.py` 的 `to_naive(now())` 生成 CST naive datetime 再入库（PyMySQL 不会对 aware datetime 做 tz 归一化）。JWT 的 `iat`/`exp` 仍使用 UTC（RFC 7519 约定），由 `core/security.py` 保持不变。前端展示（`common.js fmtTime`）以浏览器本机时区归一化为最终显示，业务字面量 CST 在用户本机为东八区时与系统时钟一致。历史以 UTC 字面量落库的旧数据需迁移或前端兼容（当前 demo 数据已统一 CST 表达，无需迁移）。

## 9. RBAC 实现约束（P0，必须严格遵循）

1. **权限编码**格式：`{module}:{action}`，与 §8 映射表完全一致。
2. **权限树**：permissions 表按 `parent_id` 组织。menu 可嵌套；button/api 挂到所属 menu 之下。
3. **多角色并集**：权限取并集；`data_scope` 取最高级（1本人 < 2本部门 < 3全部，取最大）。
4. **接口权限校验**：`require_permission(code)` 依赖查 `user_roles → role_permissions → permissions.code`；查询结果缓存（内存或 Redis，TTL 5 分钟，权限变更时失效）。
5. **数据权限**：data_scope=3 放行；=2 按 `dept_id` 及子部门过滤；=1 按 `created_by = 当前用户` 过滤（业务表必须含 created_by，见 §7.1）。
6. **初始化数据必须包含**：超级管理员（`admin / 初始口令`，密码哈希）、`admin` 角色（role_key=admin，data_scope=3，拥有全部权限）、**与 §8 一致的完整权限资源树**、默认部门（如"总部"）。
7. 删除角色/权限/分类前**必须检查引用**，被引用返回 3003。
8. **权限码一致性验收**：§8 映射表、`backend/seed/base.py` 的 PERM_TREE 权限种子、`/auth/me` 返回的 permissions 三者必须一一对应（见 §14 验收）。

## 10. 核心业务规则约束

### 10.1 订单状态机（order_status）
```
1待付款 → 2待发货 → 3已发货 → 4已完成
   │         │          │
   └──5已取消(未付款可取消)
                 └──6售后中（发起售后后）
```
- 状态流转必须写 `order_logs`（操作人、动作、时间）。
- 发货：仅 `2待发货` 可发货，写物流公司/单号，状态→3，记录日志。
- 修改价格：仅 `1待付款` 可改，记录日志。

### 10.2 商品与 SKU 规则
- 商品下架后不可下单。
- **库存扣减并发控制（强制）**：下单扣库存必须使用原子条件更新，禁止"先查后扣"裸流程：
  ```sql
  UPDATE goods_sku SET stock = stock - 1, version = version + 1
  WHERE id = ? AND stock >= 1 AND status = 1;
  ```
  - 受影响行数为 0 即库存不足，返回 3001 并回滚整个订单事务。
  - 秒杀场景：同一商品并发扣减同样遵循上述原子更新；如需更强保护，可叠加 Redis 预扣（实现自选，但原子 SQL 为底线）。
- 多规格商品：SKU 库存之和为 goods.stock 口径，保存商品时同步更新。
- 删除分类前检查：存在子分类或关联商品则返回 3003。
- 商品审核流：默认关闭（新增即上架）；若系统配置开启"新商品需审核"，新增商品 status=0 + audit_status=1，经 `POST /goods/{id}/audit` 通过后 status=1。

### 10.3 营销叠加规则
- 叠加规则以 `is_stackable` 字段为准，同类型活动（优惠券×2、满减×2）互斥。
- 默认矩阵：**优惠券 + 满减可叠加；秒杀价不参与任何叠加；拼团价不参与优惠券**。
- 具体矩阵：

| 组合 | 是否允许 |
|---|---|
| 优惠券 + 满减 | ✅ 允许 |
| 秒杀 + 优惠券 | ❌ 不允许 |
| 秒杀 + 满减 | ❌ 不允许 |
| 拼团 + 优惠券 | ❌ 不允许 |

### 10.4 积分
- 积分变动必须写 `points_logs`；手动调整必须记录原因；积分不可为负（不足时返回 3001 同义业务错误）。

### 10.5 操作日志
- 登录、退出、新增、修改、删除、导出六类操作必须写 `admin_logs`（主流程内写入，不得丢失；如为异步写入需保证最终一致）。

## 11. 配置约束

- 数据库连接、JWT 密钥、Redis 地址、上传目录等**必须**通过环境变量或 `config.py` 读取，禁止硬编码。
- 提供 `.env.example`：`DB_HOST=127.0.0.1`、`DB_USER=root`、`DB_PASSWORD=<你的MySQL口令>`、`DB_NAME=aaashop`、`JWT_SECRET`、`JWT_EXPIRE_MINUTES=120`、`UPLOAD_DIR`、`GOODS_AUDIT_ENABLED=false`、`CORS_ORIGINS`（跨域放行来源列表；商城前台独立部署于 8000 时示例值 `http://127.0.0.1:8000`）、`STATIC_MANAGER_DIR`（管理端静态目录，默认 backend 同级 manager/）、`STATIC_FRONT_DIR`（原 front 静态目录；front 改由 8000 独立静态服务托管后，后端不再 mount `/front`，此配置停用，仅兼容保留）。
- 依赖由 **uv** 管理（`uv init` 初始化 + `uv add` 新增），提供 `pyproject.toml` 与 `uv.lock` 锁定版本。

## 12. 安全约束（强制）

- 所有 SQL 参数化（`cursor.execute(sql, params)`），禁止字符串拼接。
- 密码 bcrypt 哈希；登录失败统一提示"用户名或密码错误"（防账号枚举）。
- 登录失败连续 5 次锁定账号 15 分钟（DB 记录失败次数与锁定时间，重启不丢失）。
- JWT 中只放 `user_id`、`username`、`role_keys`，不放敏感信息。
- 管理端接口全部鉴权；CORS 仅允许配置的前端来源。
- 导出数据量上限单次 5 万行。
- 富文本详情 `detail_html` 入库前需做 XSS 过滤（白名单标签），接口返回前不再信任。

## 13. 代码风格与质量门禁

- PEP8；`ruff`/`black`；函数必须有 docstring。
- 接口入参用 Pydantic 模型校验，禁止裸 `Request` 手动解析。
- 全局异常处理器统一转 `{code, message}`。
- 每个 P1 模块至少包含：路由文件、service、Pydantic schema、SQL 初始化。
- 完成一个模块 = 该模块接口可用 curl 实测通过（见 §14 验收）。
- 数据库字段 → API 字段转换集中在 service 层（snake_case → camelCase）。

## 14. 验收标准（Definition of Done）

### 14.1 功能验收
1. **可启动**：按 README 一条命令拉起服务，`GET /api/v1/health` 通过。
2. **RBAC 生效**：无 token 访问受保护接口返回 401；无权限 code 返回 403；admin 全通。
3. **初始化数据存在**：`python -m seed.runner base` 执行后存在超级管理员、admin 角色、默认部门、完整权限树。
4. **权限码一致性**：§8 映射表 ↔ `backend/seed/base.py` PERM_TREE ↔ `/auth/me.permissions` 三方比对，逐码一致，无缺码/多码。
5. **核心闭环**（curl 或自动化脚本）：
   - 登录 → 建角色 → 分配权限 → 建管理员绑角色 → 新管理员登录 → 按权限访问。
   - 建分类/品牌 → 建商品（含多 SKU，整单提交）→ 列表筛选/批量上下架 → 导出。
   - 建订单（或 seed）→ 改价 → 发货 → 详情与操作日志。
   - 发起售后 → 审核 → 完成；积分调整 → 流水可查。

### 14.2 契约验收
6. **统一返回格式**：所有接口符合 §4.1；分页结构一致；字段命名 camelCase。
7. **错误码**：库存不足返回 3001、状态不允许返回 3002、删除被引用返回 3003、无权限返回 4001，可被前端识别。

### 14.3 自动化与性能验收
8. **自动化冒烟测试**：`backend/tests/` 下的 pytest 用例，覆盖 §14.1 第 5 条全部闭环，`uv run pytest` 一条命令全部通过。
9. **性能底线（目标值，未做压测背书）**：期望商品表 10 万条数据下商品列表接口（带筛选分页）P95 < 500ms，订单列表走 `created_at` 索引 P95 < 500ms。**当前仓库没有压测脚本与压测数据，该指标尚未验证**；索引设计见 §7，已知限制见 README §10。
10. **日志落库**：关键操作在 `admin_logs` 可查到。
11. **安全验收**：DB 中 admin_users.password_hash 全为 bcrypt；登录失败 5 次触发锁定。

### 14.4 文档验收
12. **README 完整**：启动步骤、默认账号、接口清单概览、口径说明、审核流开关说明。
